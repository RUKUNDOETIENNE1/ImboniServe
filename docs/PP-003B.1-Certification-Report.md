## 2. Workflow Validation

### Application Lifecycle States

```
SUBMITTED → UNDER_REVIEW → APPROVED (terminal)
                         → REJECTED (terminal)
                         → WITHDRAWN (terminal)
SUBMITTED → APPROVED (skip review, allowed)
SUBMITTED → REJECTED (allowed)
SUBMITTED → WITHDRAWN (allowed)
```

### Actions Implemented

| Action | Roles | API Action | Service Method |
|--------|-------|------------|----------------|
| Start Review | ADMIN, PARTNERSHIP_MANAGER | `review` | `FounderPartnerApplicationService.review()` |
| Approve | ADMIN, PARTNERSHIP_MANAGER | `approve` | `FounderPartnerApplicationService.approve()` → triggers onboarding |
| Reject | ADMIN, PARTNERSHIP_MANAGER | `reject` | `FounderPartnerApplicationService.reject()` |
| Withdraw | ADMIN, PARTNERSHIP_MANAGER | `withdraw` | `FounderPartnerApplicationService.withdraw()` |
| Assign | ADMIN, PARTNERSHIP_MANAGER | `assign` | Updates `reviewedBy`, logs activity |
| Add Note | ADMIN, PARTNERSHIP_MANAGER | `addNote` | `PartnershipService.logActivity()` |
| View | ADMIN, PARTNERSHIP_MANAGER, SALES, SUPPORT, LEGAL, EXECUTIVE | GET | Read-only access |

### Invalid Transitions Blocked

- APPROVED → REJECTED (terminal state)
- REJECTED → APPROVED (terminal state)
- WITHDRAWN → any (terminal state)
- Non-management roles cannot perform actions (403)

## 6. Performance Notes

| Aspect | Implementation |
|--------|----------------|
| Server-side pagination | API accepts `limit` and `offset` params; default 25 per page |
| Search | Server-side Prisma `contains` with `insensitive` mode |
| Data loading | Single API call for detail page (application + timeline + audit + risk + health) |
| Rendering | No client-side virtualization needed at current scale; table renders max 25 rows per page |
| Caching | No client-side caching; fresh data on each navigation |
| Bundle | Components are lightweight, no additional dependencies beyond existing lucide-react |

### Scalability Considerations

- For 50,000+ applications: API already supports server-side pagination and filtering
- Search uses indexed Prisma queries (email, name, organization)
- Timeline query limited to 200 entries; audit limited to 100
- Future: Add cursor-based pagination for deeper pages; consider virtualized list for >100 items

## 7. UXG-001 Navigation & Workflow Review

### Navigation Flow Assessment

| Flow | Steps | Status |
|------|-------|--------|
| Admin → Applications List → Detail → Approve | 3 clicks | ✅ Optimal |
| Admin → Applications List → Detail → Reject | 3 clicks + reason | ✅ Optimal |
| Admin → Applications List → Detail → Start Review | 2 clicks | ✅ Optimal |
| Admin → New Application → Submit | 1 click + form | ✅ Optimal |
| Admin → Applications List → Search → Detail | 2 clicks + search | ✅ Optimal |

### Workflow Completeness

| Requirement | Status |
|-------------|--------|
| Task-oriented (not CRUD) | ✅ Actions are review-specific (Start Review, Approve, Reject) |
| Minimize navigation steps | ✅ All actions available on detail page |
| Lists surface actionable info | ✅ Status, applicant, wait time, overdue indicator, reviewer |
| Permissions enforced | ✅ Both server-side and client-side |
| Full context on detail page | ✅ Profile, application info, risk, timeline, audit, notes |
| Audit trail | ✅ Read-only audit tab with old/new values, performer, timestamp |

### Mobile Responsiveness

| Breakpoint | Behavior |
|------------|----------|
| Desktop (lg+) | Full table with all columns visible |
| Tablet (md) | Organization column hidden, table remains scrollable |
| Mobile (sm) | Essential columns only (applicant, status), horizontal scroll for details |

### Findings

- **No blocking issues found.**
- All required workflows are accessible within 3 clicks from admin home.
- Action buttons are contextually shown only when valid (e.g., "Start Review" only for SUBMITTED status).
- Overdue indicator (red alert icon) surfaces applications waiting >5 business days.
- Internal notes allow team collaboration without leaving the detail page.

## 9. Engineering SOP

### Adding a New Application Action

1. Add the action case to the PATCH handler in `src/pages/api/admin/partnership-applications/[id].ts`
2. Call the appropriate service method from `FounderPartnerApplicationService`
3. Add the action button to the detail page in `src/pages/admin/partnership-applications/[id].tsx`
4. Guard with `canManage` check for role-based visibility
5. Add test case to `tests/components/partnership-applications.test.tsx`

### Adding a New Status Type

1. Add the status to `StatusBadge` config in `src/components/partnerships/StatusBadge.tsx`
2. Add the status to `ApprovalBanner` config in `src/components/partnerships/ApprovalBanner.tsx`
3. Update the `STATUS_FILTERS` array in the list page
4. Add workflow transition test in the test file

### Modifying Permissions

1. Update the role check in `getServerSideProps` of the page
2. Update the role check in the API route handler
3. Update the `canManage` / `canViewAudit` flags in the detail page
4. Update permission matrix tests
