## 1. Executive Summary

This manifest is the **single authoritative reference** for reconstructing the ImboniServe database. It eliminates ambiguity by defining, for every database object and supporting artifact: the canonical source of truth, whether it must be reconstructed, how it should be reconstructed, in what order, and how reconstruction will be verified.

1. **Prisma migrations are the canonical source for schema.** `prisma migrate deploy` is the primary reconstruction mechanism.
2. **Prisma schema (`schema.prisma`) is the canonical source for model definitions.** `prisma validate` and `prisma generate` verify schema integrity.
3. **Two migrations contain FK errors** (`REFERENCES "Business"` instead of `"Restaurant"`) that must be corrected before `migrate deploy` can succeed.
4. **One standalone SQL file is required** (`scripts/sql/add_payment_health_indexes.sql`) — creates indexes not in Prisma schema.
5. **RLS is enabled without policies** — a decision is required: create policies or disable RLS.
6. **One table (`CostAnomalyAlert`) exists outside Prisma** — managed via raw SQL, accessed via `$queryRaw`.
7. **Three manual operations are required** — Supabase project creation, storage bucket creation, environment variable configuration.

### Reconstruction Readiness: **Ready for Controlled Reconstruction** (with 3 pre-conditions)

**Pre-conditions:**
1. Fix 7 FK references from `"Business"` to `"Restaurant"` in 2 migration files

## 2. Reconstruction Authority Hierarchy

The following hierarchy defines which source takes precedence when conflicts exist. **Higher = more authoritative.**

| Priority | Authority | Scope | Justification |
|----------|-----------|-------|---------------|
| **1** | **Prisma schema** (`prisma/schema.prisma`) | Model definitions, field types, relations, indexes, enums | The canonical declaration of intended database structure. `prisma validate` confirms internal consistency. `prisma generate` confirms client compatibility. |
| **2** | **Prisma migrations** (`prisma/migrations/*/migration.sql`) | DDL execution sequence | The executable history of schema changes. `prisma migrate deploy` applies them in order. This is the reconstruction mechanism. |
| **3** | **Seed scripts** (`prisma/seed.ts`, `prisma/seeds/*.ts`, `scripts/seed-*.ts`) | Reference data | The canonical source for initial data population. |
| **4** | **Required standalone SQL** (`scripts/sql/add_payment_health_indexes.sql`) | Performance indexes not in Prisma | Creates concurrent indexes that cannot be expressed in Prisma schema. Must be run after Prisma migrations. |
| **5** | **Raw SQL migrations** (`20260616130000_recreate_cost_anomaly_alert`) | Tables outside Prisma schema | The only way to create `CostAnomalyAlert` which is not modeled in Prisma. |
| **6** | **Application initialization logic** (`src/lib/monitoring/startup-checks.ts`) | Runtime verification | Validates database connectivity at startup. Not a reconstruction source. |
| **7** | **Supabase configuration** (Dashboard) | Storage buckets, project settings | Manual configuration outside the repository. |
| **—** | **Standalone SQL files (non-required)** | — | **Excluded from reconstruction.** See Section 8. |
| **—** | **Loose SQL files in `prisma/migrations/`** | — | **Excluded from reconstruction.** See Section 8. |

### Authority Resolution Rules

1. If Prisma schema and a migration conflict, **schema wins** for model definition, **migration wins** for execution.
2. If a Prisma migration and standalone SQL create the same table, **Prisma migration wins**. Standalone SQL is excluded.
3. If two migrations modify the same object, **later migration wins** (chronological order).
4. If a migration references a non-existent table (`"Business"`), **the migration must be corrected** to reference the physical table name (`"Restaurant"`).
5. If a table is not in Prisma schema but is in a migration and used by application code, **the migration is canonical** for that table.

## 11. Engineering Risks

| # | Risk | Severity | Mitigation |
|---|------|----------|-----------|
| 1 | **FK fix changes are modifications to migration files** | Medium | Migrations are normally immutable. Changing them creates a divergence from the original repository. Document the change clearly. On a fresh DB, this is safe because the migrations have never been applied. |
| 2 | **`ALTER TYPE ADD VALUE` in transaction** | Low | Supabase uses PG 15 which supports this. If running on older PG, would fail. Verify PG version before deployment. |
| 3 | **`gen_random_uuid()` without pgcrypto** | Low | PG 13+ includes `gen_random_uuid()` in core. Supabase uses PG 15. No issue expected. |
| 4 | **Empty migration `20260304_trial-eligibility`** | Low | Tables are created in migration `20260324075113`. Empty migration is a no-op. No issue. |
| 5 | **`dev-start.bat` falls back to `db push`** | High | **Do NOT use `dev-start.bat` for reconstruction.** Use manual `prisma migrate deploy` instead. `db push` would create tables without migration history. |
| 6 | **CostAnomalyAlert outside Prisma schema** | Medium | Table is created by migration `20260616130000`. Application accesses via `$queryRaw`. If migration fails (FK issue), table won't exist. Fixed by Step 0b. |
| 7 | **RLS without policies blocks application access** | High | Must be addressed in Step 0c/2d. If not addressed, application will get empty results for Recipe, RecipeIngredient, InventoryConsumption. |
| 8 | **Concurrent indexes via pg_cron** | Low | `add_payment_health_indexes.sql` uses pg_cron to schedule index creation. Indexes may not be immediately created — may take 1-2 minutes. Verify after a short delay. |
| 9 | **Seed data inconsistency** | Low | `seed.ts` creates plans, `plans-phase2.ts` updates them. Running both in order (3a then 3b) is correct. Running only one may result in inconsistent plan data. |
| 10 | **No CI/CD migration pipeline** | Medium | Reconstruction is entirely manual. Human error risk. Follow this manifest step-by-step. |
